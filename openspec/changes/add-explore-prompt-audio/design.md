## Context

Explore games generate exercises on-device through `LocalExploreProvider`; each
exercise carries a child-facing `promptVi` and an `audioRefs` array that is empty
for every game today except a placeholder on tracing. The prompt strings come from
a finite grammar:

- Fixed, parameterless phrases — e.g. `numberGame` `'Con hãy tìm số giống mẫu.'`,
  `'Số nào còn thiếu?'`, `'Con hãy xếp các số từ bé đến lớn.'`; `memoryGame`
  `'Con hãy lật thẻ và tìm các cặp giống nhau.'`; `routePlannerGame`
  `PROMPTS[level]`; the `patternGame` prompt heads.
- Parametric templates with enumerable slots — `Con hãy chọn số ${answer}`,
  `Số nào đứng ${trước|sau} số ${reference}?`

kido-pipeline already generates Vietnamese TTS: `tts.service.synthesize(text,
'vi', { wrap })` (Google GenAI, PCM→WAV 24 kHz, throttled), with `wrap:false`
meaning "pronounce exactly this text, no narration wrapper." Reusable clips live
in `audio_library` keyed by `{ audioId (ASCII word-key), lang }`, unique per
language, with a `pending → generating → pending_review → approved | rejected`
lifecycle — the same review discipline the product requires before any generated
audio ships. `vi-label.ts` / curriculum §6.2 fix a Northern (Bắc) voice for that
library.

The mobile side already has a bundled best-effort Explore audio contract
(`explore/audio.ts`: only approved bundled clips, missing/failed is swallowed,
never a required dependency) and, via `add-explore-sound-effects`, a settings-aware
best-effort playback foundation. Lesson audio streams from a bucket
(`speech.ts` + `assetCache`), but `enable-explore-offline-audio` deliberately
rejected streaming for Explore to preserve offline-first play.

## Goals / Non-Goals

**Goals:**

- Read every enabled Explore game's question aloud in Vietnamese, offline.
- Cover the finite prompt space with a composable, reusable clip inventory
  (fixed-phrase clips + slot clips) instead of per-prompt recordings.
- Use kido-pipeline (`tts.service` + `audio_library`) as the single reviewed
  generator of that inventory, and export it as a versioned bundled pack + static
  registry for the app.
- Keep prompt audio strictly best-effort: absence or failure falls back to the
  existing on-screen prompt and never affects generation, availability or
  completion.
- Preserve Explore's offline, stateless, zero-history and no-kido-server-publish
  guarantees, and reuse (not duplicate) the number-name pack and playback
  foundation from the sibling audio changes.

**Non-Goals:**

- Runtime device/cloud TTS, or streaming Explore audio as an offline fallback.
- Publishing Explore audio to kido-server or changing lesson audio.
- SFX/feedback sound (owned by `add-explore-sound-effects`) and number/hear-select
  audio content (owned by `enable-explore-offline-audio`).
- Per-child voice, prosody variation, or any play-history-derived audio.
- Rewriting prompt copy or game generators beyond exposing their key mapping.

## Decisions

### Compose prompts from a finite keyed inventory, stitched at runtime

Each prompt is represented as an ordered list of stable audio keys, e.g.
`Con hãy chọn số 7` → [`explore-audio:vi:phrase:choose_number:v1`,
`explore-audio:vi:number:name:7:v1`]. Fixed phrases are single whole-sentence
clips; slots (numbers 0–N, a closed object-label set, four direction words) are
individual clips reused across every template that needs them. The renderer plays
the segments in order through the shared playback foundation.

Per-prompt whole-line recording was rejected: the parametric templates make the
full set combinatorial, while the composable set is small and mostly shared.
Streaming/full-line-online was rejected to keep Explore offline-first and to honor
the existing `enable-explore-offline-audio` decision.

### kido-pipeline is the reviewed generator; the app bundles the result

The inventory is generated by `tts.service.synthesize(transcript, 'vi',
{ wrap:false })` so stitched playback is exactly the authored text, stored/reused
in `audio_library` (get-or-create by word-key + `lang`), and only clips at
`approved` are eligible to export. This reuses the platform's existing TTS voice,
throttle, reuse and review machinery rather than introducing hand-recording or a
second TTS path. Number-name slots already covered by
`enable-explore-offline-audio` are reused, not regenerated.

### A new pipeline output target: a bundled app pack, not a server publish

Explore is on-device and is never published to kido-server, so the pipeline gains
a distinct, deterministic export: a versioned Explore audio pack plus the
Metro-static TypeScript registry the app imports. This keeps the app fully
offline and keeps kido-server out of the Explore path. The export runs only over
`approved` clips and records pack version + covered keys for verification.

### Best-effort, construct-preserving, zero-history

Missing or failed prompt audio degrades to the on-screen `promptVi`; audio never
gates a game. Prompt audio honors `audioEnabled`/`volume`, plays offline, and
writes no history or analytics. It does not reveal a `hear_select` answer — that
mode's audio-gating rule stays with `enable-explore-offline-audio`; this change
only voices the *instruction/question*, not answer options.

### Keep generator and inventory in sync by construction

Because the key list is derived from the same finite templates a game emits, a
test asserts that every template a game can produce maps to a fully resolvable key
list, and that every key resolves to an approved bundled clip. Adding a prompt
variant without its keys fails that test rather than silently shipping a mute
prompt.

## Risks / Trade-offs

- [Stitched sentences sound robotic at slot boundaries] → Author fixed phrases as
  whole clips so only the slot word is concatenated; review stitched playback of
  the highest-frequency templates before approval; keep a whole-line option open
  for a few awkward prompts.
- [Generator adds a prompt variant without audio keys] → Composition-coverage
  test fails closed; missing key degrades to on-screen text at runtime.
- [Inventory/registry drifts from approved clips] → Generate the registry from the
  exported pack and test every static module resolves in a production bundle.
- [Bundle size grows with the inventory] → Finite, mostly-shared set; reuse the
  number pack; compress consistently; record pack size in release checks.
- [Northern-voice/pronunciation inconsistency] → Single reviewed voice via
  `audio_library`; listen-check per curriculum §6.2 before approval.
- [Scope bleed into kido-server] → Explicit non-goal + no publish path touched;
  export target is the app bundle only.

## Migration Plan

1. Define the prompt→key mapping and the key-naming scheme next to each game's
   prompt generator (mobile), with no assets yet — everything degrades to text.
2. Enumerate the inventory (fixed phrases + slots) and generate it in kido-pipeline
   via `tts.service`/`audio_library`; review to `approved`.
3. Add the pipeline export: versioned pack + generated static registry; bundle it
   into the app under `mobile/src/assets/audio/explore/`.
4. Implement the runtime stitching resolver and wire prompt playback through the
   shared foundation; add replay control.
5. Verify composition coverage, airplane-mode playback, best-effort fallback, no
   history/side effects; lint mobile and test/build pipeline. Roll back by not
   exporting the pack — prompts remain on-screen text.

## Open Questions

- Exact key-naming scheme and versioning — align with the existing
  `explore-audio:vi:...:v1` convention already used in `tracingGame`.
- Which few prompts (if any) are better as whole-line clips than stitched, for
  naturalness, and what is the pack's compressed size budget?
- Should the pipeline export be a new CLI script (e.g. `npm run explore:audio`) and
  where does the exported pack live in the repo vs. the app bundle?
- Should `wrap:true` (gentle narration) ever be used for fixed phrases, or is
  `wrap:false` exact-text synthesis mandatory for predictable stitching?
- Coordination/order with `enable-explore-offline-audio`: land after it (reuse its
  0–50 pack + registry) or fold the number pack generation into this routine?
